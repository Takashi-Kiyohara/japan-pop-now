## Phase 1: GSC URL list 取得 (10 分)

GSC CSV は issue type count のみで URL list 別。user に 5 export 依頼 or Code 側で sitemap 全 URL を curl で status check して類推。

**Code 側自力取得 (推奨)**:
```bash
# sitemap 全 article URL を curl で final status check
curl -sA "Mozilla/5.0" "https://www.japan-pop-now.com/sitemap.xml" | grep -oE "<loc>[^<]+</loc>" | sed -E 's|</?loc>||g' > /tmp/all_urls.txt

# 各 URL の status + redirect chain を tabulate
while IFS= read -r url; do
  status=$(curl -sA "Mozilla/5.0" -o /dev/null -w "%{http_code} %{redirect_url} %{num_redirects}" "$url")
  echo "$url | $status"
done < /tmp/all_urls.txt > /tmp/url_status.tsv

# 異常 URL 抽出 (200 直接ではないもの)
awk -F'|' '$2 !~ /^ 200/' /tmp/url_status.tsv > /tmp/issues.tsv

# 内訳カウント
awk -F'|' '{split($2, a, " "); print a[1]}' /tmp/url_status.tsv | sort | uniq -c | sort -rn
```

**output 期待**: 35 件 issue の URL 別 list、status code + redirect chain depth。

## Phase 2: 4 group ごとの fix logic (1-2h)

### Group A: redirect chain depth >1 (20 件想定)

**症状**: URL A → URL B → URL C → 200 のような multi-hop。Google は **2 hop で再 crawl 諦める**ことが多い。

**fix**: chain の **最初の URL を最後の final 200 URL へ直接 301 化**。
- 中間 hop の URL が live にあれば middleware / next.config.ts redirects 配列を最適化
- chain 起点が legacy WP URL (例: `?p=NNN`, `/category/anime/`) なら 410 Gone 化推奨 (memory `feedback_legacy_wp_unsplash_trap` 参照、WP URL は 410)

**実装場所候補**:
- `next.config.ts` redirects 配列
- `middleware.ts` の URL rewrite

**verify** (push 後):
```bash
for url in <chain origins>; do
  curl -sA "Mozilla/5.0" -o /dev/null -w "%{http_code} %{redirect_url} %{num_redirects}\n" -L "$url"
done
# expected: num_redirects ≤ 1, final 200 (または意図的 410)
```

### Group B: 404 (2 件)

**症状**: sitemap に含むが live で 404。

**fix**:
1. もし「期間限定 collab post-event」= **410 Gone** (Vercel route で `revalidate: 0` + response status 410、または `app/[deleted_slug]/route.ts` で `new Response(null, { status: 410 })`)
2. もし「sitemap に含むけど article 削除済」= sitemap.xml から落とす (`app/sitemap.ts` の filter 修正)

**verify**:
```bash
for url in <404 URLs>; do
  curl -sA "Mozilla/5.0" -o /dev/null -w "%{http_code}\n" "$url"
done
# expected: 410 (post-event collab) or sitemap から除外 (sitemap.xml 再 fetch で 0 hit)
```

### Group C: 代替ページ canonical (4 件)

**症状**: live HTML の `<link rel="canonical">` が別 URL を指してる、または自己 canonical 形式不整合 (e.g., trailing slash / www / http vs https)。

**fix**:
1. canonical 自己参照に統一 (`canonical = current URL`)
2. trailing slash + https://www 形式統一 (Next.js では `metadata.alternates.canonical` で制御)
3. og:url と canonical を一致させる (sniff prevention)

**audit**:
```bash
for url in <sitemap URLs>; do
  body=$(curl -sA "Mozilla/5.0" "$url")
  cano=$(echo "$body" | grep -oE '<link[^>]+rel="canonical"[^>]+href="[^"]+"' | grep -oE 'href="[^"]+"' | sed 's/href="//;s/"//')
  if [ "$cano" != "$url" ]; then
    echo "MISMATCH: page=$url canonical=$cano"
  fi
done
```

### Group D: ページにリダイレクト (3 件)

**症状**: sitemap 内の URL が自分自身 → 別 URL に 301、つまり sitemap が legacy URL を listing してる。

**fix**:
- sitemap.xml の URL list を `redirect` 系から **redirect 後の final URL に書換** (sitemap source = `app/sitemap.ts` の article list 生成 logic)

**verify**:
```bash
curl -sA "Mozilla/5.0" "https://www.japan-pop-now.com/sitemap.xml" | grep -oE "<loc>[^<]+</loc>" | sed -E 's|</?loc>||g' > /tmp/sm.txt
while IFS= read -r url; do
  rcode=$(curl -sA "Mozilla/5.0" -o /dev/null -w "%{http_code}" "$url")
  if [ "$rcode" != "200" ]; then echo "$url -> $rcode"; fi
done < /tmp/sm.txt
# expected: 0 (sitemap 全部 final 200 URL のみ)
```

## Phase 4: live verify (push 後 30 秒待ち)

